# Changelog

## 0.35.0

### Security

- **A row was held to the scope of the type a field returns only when it was a row of that type's own model.** With `DocumentType.scope_rows` hiding drafts and `MemoType` over a subclass of `Document` (a Django proxy or multi-table child, a Tortoise model inheriting it, an inherited SQLAlchemy mapping), a `DocumentType` field that handed out draft memos showed them. That covered a plain `orm.field.lazy` or `@strawberry.field` returning a query, rows or one row, `strawberry.relay.connection(ORMListConnection[DocumentType])` (which counted them in `totalCount` too), `orm.payload.query`, `node(id:)`, `nodes(ids:)`, `relay.Node` lists, `Folder.memos` and `orm.field.lazy(filters=MemoFilter)`. A row is now held to the scope of every type it may be read as: its own class's, the field's declared type's (through connections, edges and payloads), and, under an interface or union, the type it resolves to. On Tortoise, a row of a model inheriting another with no `scope_rows` of its own was checked against the base's table, so memo 3 was shown because document 3 was published; rows are now checked against their own class's table.
- **A row scope that limited its rows allowed different rows on each surface, and one allowing none could allow all of them.** Tortoise drops a zero limit from the `values()` queries a scope is built into, so with `scope_rows` returning `qs.limit(0)`, filters through a relation, `has`/`lacks`, groups, aggregates, a relation's `totalCount` and to-one relations read every row. A positive limit counted other rows wherever the scope went into another statement, and even at the root the client's filter and order picked the rows it kept: with `order_by("id").limit(2)`, `posts(filter: {field: {title: {inList: ["Draft Post", "Rust Adventures"]}}})` returned posts 3 and 4. A repo's `scope_query` had the same flaw on writes: a write's lookup put its own `.first()` or `.limit(2)` on top, replacing a limit of none, so a repo that denied every row with `.limit(0)` let ref updates, deletes, unlinks, upsert matches and nested updates through. A scope allowing no rows (`.limit(0)`, `[:0]`, `.none()`) now hides every row on every read and write, and a `scope_rows`, `scope=` or `scope_query` that adds a limit, offset or `FETCH` is refused. A limit set by the field's own resolver is kept.
- **Counts over a scope that joins or groups counted a row once per joined row.** A relation connection's `totalCount` and a windowed group's count under `qs.annotate(n=Count("comments")).filter(n__gte=1)` reported Alice's 2 posts as 3 on Django and Tortoise. Each row is now counted once.
- **Errors were masked by a list of types, and each list missed some.** Django's `FieldError`, `ValidationError`, `ObjectDoesNotExist` (`Post matching query does not exist.`), `MultipleObjectsReturned` and `EmptyResultSet`, Tortoise's errors outside `OperationalError` and `FieldError` and every driver error its client does not translate, raw `sqlite3` errors, and on every backend any error raised while a `scope_rows` or `scope=` built its query, reached the client with tables, columns, model classes and bound values. A Tortoise field validator answered `filter: {field: {ledgerCode: {inList: ["zzz"]}}}` with `Value 'zzz' does not match regex '^ACME-[0-9]{4}-INT$'`, and a lone surrogate in a JSON variable made SQLite raise a `UnicodeEncodeError` that passed through as it was. Every backend now masks, on reads and writes alike, any error the ORM raised itself or that was raised in a call made while it built or ran a statement (a field preparing a value, the driver binding it), whatever its type, as `Invalid filter expression` or `The database refused the write`, with the original as `__cause__`. An error raised in this library's own code keeps its message.
- **Refusals named the app's Python classes.** `Cannot group by Post.tags through post`, `objects: {tags} on Post` and `Cannot order by Comment.document: Document has subclasses scoped by their own types' scope_rows (Contract) …` now name only what the client wrote, and the full message is the error's `__cause__`.
- **A `using=` resolver read whatever a relation held, trusting that a scoped load had been planned for it.** On SQLAlchemy, `@orm.field.computed(using=["author"])` read an author `UserType.scope_rows` hides when the mapper loaded `Post.author` with `lazy="selectin"` or `"joined"`, when the root returned `aliased(Post)` or `with_polymorphic(...)`, when the rows came from the identity map or a list the app keeps, when a sibling field had loaded the relation without the edge's `scope=`, or when the optimizer was off. On Django and Tortoise the same happened with the optimizer off and over rows the app keeps. The deprecated `orm.field(using=…)`, `orm.field.auto(using=…)` and `orm.field.scoped(using=…)` were built without any such check, so a model property behind them showed a post's hidden author or an author's unpublished posts wherever the plan had not filled the relation. A `using=` resolver, deprecated forms included, now runs only once every relation on its paths holds exactly what this execution loaded under the related type's `scope_rows` and the field's `scope=`; any other relation is read again under them first.
- **SQLAlchemy: a relation the mapper loads with `lazy="joined"` came back unscoped.** With `Post.author = relationship(lazy="joined")`, `{ posts { author { name } } }` showed an author `UserType.scope_rows` hides, and `{ authors { posts { title } } }` listed drafts. A scoped relation is now read by a statement of its own, the mapper's eager load is held off for it, and only that statement marks it as scoped.
- **Concurrent loads could fill a relation between the scoped load and the check that trusted it.** On an SQLAlchemy `AsyncSession` or with `offload_sync_session`, a `staffAuthors { posts { title } }` field beside `authors { posts { title } }` loaded every post onto the shared rows while the guest's load waited, and the guest's list showed the staff-only post. On Tortoise, an app's `Prefetch` on a relation (`Author.all().prefetch_related(Prefetch("posts", Post.all()))`) raced the scoped prefetch, and whatever the relation held afterwards was marked as scoped. A relation is now marked only by the statement that loaded it, together with the rows it loaded, and readers check and return that same value; Tortoise runs an app's prefetches first and the scoped prefetch after them.
- **Adding `permission_classes` to a scoped field dropped its scope, and a `strawberry.field(...)` on a relation replaced the library's resolver.** `posts: list[PostType] = orm.field.eager(scope=published, permission_classes=[IsAuthenticated])` returned unpublished posts whenever the plan had not loaded them, and `author: UserType | None = strawberry.field(permission_classes=[IsStaff])` read `row.author` as the ORM had loaded it. An `orm.field.eager()` or `orm.connection.eager()` the library could not build (a connection subclass, `ORMListConnection["PostNode"]`, annotations under `from __future__ import annotations`, `names: list[str] = orm.field.eager()`) stayed a plain attribute and read whatever the row held, unpaged. The permission now runs around the library's scoped resolver, a `strawberry.field(...)` on a relation adds its options to the field the library builds, and a field that cannot be built raises `ValueError` naming it.
- **Under an interface, a union or Relay's `node`, the optimizer planned `using=` paths and `scope=` for whichever type over the model was registered first.** With `StaffUser` (plain `posts`) registered before `PublicUser` (`posts` with `scope=published_only`), `{ people { ... on PublicUser { postTitles } } }` read Bob's `Draft Post` on every backend, and `using=["posts.comments"]` skipped `CommentType.scope_rows`. Rows cast with `strawberry.cast` are now planned as their own type, and rows whose type cannot be told ahead load each relation with only the rows every candidate type's `scope=` allows.
- **A `strawberry.cast` outlived the request that made it.** The cast is an attribute on the row, and the library's list fields, `node()` and `nodes()` cast every row they return, so where rows outlive a request (a cache, a long-lived session's identity map) a staff request left a row typed `StaffMember`, and a guest's `list[Named]` then read its `email`. Concurrent requests also overwrote each other's casts. A cast now holds only in the execution that made it.
- **Hiding rows from a list a resolver returned changed the app's list.** A resolver returning a SQLAlchemy relation's own collection (`return user.posts`) had the rows `scope_rows` hides taken out of a copy that was still bound to the parent, so the next flush set their `author_id` to `NULL`: a guest's read rewrote the database. The rows are now left out of a plain list, and the app's list and the collection it belongs to are left as they were.
- **A write asked `authorize=`, the repos' `can_*` and their `scope_query` about only some of the models a row belongs to.** A SQLAlchemy upsert matching a polymorphic `Contract` through `Doc` asked `authorize` only about `Contract`, so a callback refusing `("upsert", Doc, 2)` let it through; a Django multi-table child read through its base was asked about only as a `Doc`; and a row with a repo of its own skipped the base repo's `can_*`. A write reaching a row as a row of a subclass looked it up under that subclass's `scope_query` alone, so a docs repo hiding other users' docs by `scope_query`, as the README recommends, did not hide them from an upsert on a sealed-doc subclass. Every write, on every path, sync and async, now asks `authorize` and the `can_*` hooks about the input's model, the row's own model and their bases, and a row must be one each of their repos' `scope_query` shows.
- **An update saved more than it decided, after its checks.** On Django a write saved each row it updated with `save()`, and on Tortoise with a `save()` of every column, so a column another request changed after the write read the row (an `owner_id`, a `tenant_id`, an `is_published`) was set back to what the write had read, through root, nested and ref-list updates, the doc above a nested write, a link's `update`, a one-to-one moved to another row, a multi-table child, an override of `_save` and a soft delete through it; Tortoise's ref-list link and unlink did the same to the row they moved. A row deleted in between was inserted again by Django, without `can_create` being asked, and Tortoise reported it updated. A row a write read is now saved with an `UPDATE` of the fields the write set, those a hook returned or assigned on the row, and the columns the ORM stamps on a save, and a write that would set a column of a row no longer there is refused as `The database refused the write`. SQLAlchemy's unit of work already saved only what changed, and now writes a column the write set to the value it read too.
- **A delete took rows other repos govern with it.** `{delete: {id: "1"}}` on an article let Tortoise's default `on_delete=CASCADE` delete its remarks, though `RemarkRepo.can_delete` returns `False`. Django's `CASCADE` and `DB_CASCADE`, SQLAlchemy's `cascade="all"` / `"delete-orphan"` and `ondelete="CASCADE"` foreign keys did the same, through nested deletes, `onReplace: DELETE` and delete-orphan links. The library now lists the rows a delete takes with it, and refuses with `PermissionError` unless each governed row is shown by its repo's `scope_query`, allowed by its `can_delete` and not denied by `authorize`.
- **Writes could set the key of the row they wrote, and so write another row.** On Django, `orm.input(Contract)` (a multi-table child of `Doc`) offered the inherited `id`, so `{create: {id: 4, title: "x"}}` in `Binder.contracts` updated document 4, a row no repo was asked about, and turned it into a contract; the parent links (`doc_ptr`, `doc_ptr_id`, a named `parent_link`) did the same through `include=`, node inputs and `_meta`. On Django and Tortoise, an `on_before_update` returning `{**data, "id": 1}` for row 2 saved its values onto row 1. Node inputs offered a one-to-one link that is the row's key, and re-pointing it moved the row onto another parent's, and moving a row keyed by its link to a parent took the key of the row already there. Generated inputs now leave out every key and parent link along a model's inheritance chain and links that are a row's own key, a Django multi-table child is created with an `INSERT` into every table, and update data that sets a key, or a move that would, is refused with `UpsertValidationError`.
- **Relation batching merged sibling queries that differed in everything but their SQL.** On Django, Alice's `prefetch_related(Prefetch("comments", …, to_attr="shown"))` showing every comment and Charlie's showing only his own ran as one query, so Charlie read Bob's note; prefetch lookups, `values()`, proxies, `QuerySet` subclasses, custom iterables, `fetch_mode()`, rows already read and parameters whose `repr` hid their value were ignored the same way. On SQLAlchemy, a `Select` subclass, an attribute set on the statement (which `do_orm_execute` can read), a second class mapped to the same table and parameters with a hiding `repr` were ignored, so Alice saw Bob's drafts, and rows were handed out by column name, so with a key mapped under another name a `writer_id` property handed Ben's article to Ann. A query now batches only when every piece of state it holds is understood and identical, and rows go out by the mapped attribute.
- **A tagged argument came back when a field extension rebuilt the field's arguments, and filter, order and group inputs kept columns a tagged schema hides.** With `secret: Annotated[bool, strawberry.argument(metadata=tags("internal"))]`, `orm.payload.mutation(input_mutation=True)` or `extensions=[InputMutationExtension()]` put `secret` in the `input` of a schema built with `tags="public"`, and it reached the resolver. `@orm.filter_type`, `@orm.order_type` and `@orm.group_type` dropped the tags of the fields they declare, so `email` was offered in `filter`, `order` and `groupBy`. And which types an input serves was read off the declared field rather than the copy a tagged schema serves, so a filter an extension added to such a field kept the columns of every other type it served, columns the field's own type hides, and a client could filter by them. Tags now apply to the arguments and input fields a field has after every extension has run, generated inputs keep each declared field's tags, and an input is cut to the fields of the types the schema actually serves.
- **A tagged argument reached a tagged schema built after another schema of the same types.** Strawberry applies a field's extensions to the field itself whenever a schema converts it, and an input mutation leaves the field with an `input` whose fields carry no tags, so `orm.schema(query=Query, tags="public")` built after `orm.schema(query=Query)` served `secret` in that `input` and passed it to the resolver. The same went for an extension rebuilding the field's arguments. The arguments a tagged schema hides are now read off what the field's resolver declares, and the copy it serves applies copies of the field's extensions, so an extension keeping what it built is not left cut for the schemas built after.
- **Without the optimizer, a connection read every row its query matched, and `default_query_limit` did not cap a root list whose resolver returned a query.** With `optimizer=False`, `itemPage(first: 3)` over 30 rows loaded all 28 visible ones (Tortoise read them twice), and the same held for relation connections, connections on plain types, each group's `items` and `orm.connection.lazy`. `@orm.field.eager()` over `return select(Item)` and `orm.field.lazy(filters=…, order=…)` returned every row with or without the optimizer. Pages are now cut with `LIMIT`/`OFFSET` whether or not the optimizer is mounted, and those root lists are cut to the limit after their filter, order and scope.
- **Fragments spread under several relations made the optimizer's planning exponential in the query's depth.** The 0.34.0 fix expanded a fragment once per selection, but `fragment F0 on CommentType { parent { ...F1 } replies { ...F1 } }` nested twelve levels deep was still planned along every path: 8,190 loads and about 4.5 s on every backend before anything was read. Connections and aliases did the same, and `@skip`/`@include` were ignored. Each part of a document is now planned once per operation and shared wherever it appears, `@skip`/`@include` are honoured, and an operation may plan at most 200 relation loads plus 8 per field it writes out; past that it is refused before any row is read.
- **Regex and text lookups were not budgeted, and a regex was given every value however long.** With `enable_regex_filters=True`, one filter could hold up to `max_filter_branches` regexes, each tested on every row, on SQLite in Python's `re` inside the server process, and aliases multiplied them again; a pattern the guard allows can take time quadratic in a value's length. A filter argument, and a whole request, may now use at most `max_regex_filters` regex and iRegex lookups (default 3) and `max_filter_text_length` characters of `contains`, `startsWith` and `endsWith` text, `i` forms included (default 1,000), and Django and SQLAlchemy give a regex only values of at most `max_regex_text_length` characters (default 256).
- **A filter's values were counted but never measured.** A reference to a variable is two tokens however long its value, so one 100 kB string sent once and referenced from every `notInList` slot under four aliases was bound to the database 800 times (80 million characters from a 103 kB request) on SQLAlchemy, Tortoise and through the MCP `graphql` tool, and 125 times on Django, within every limit of the production baseline and `MaxTokensLimiter`. Every value a filter holds, each reference counted, custom filter fields and values of any type included, is now measured against `max_filter_value_length` characters (default 100,000) for the filter and for the request, before any statement is sent.
- **Refusals quoted the client's value whole.** `"<50,000 characters>" is not a valid id` on an upsert, the same for a global ID of another type and a text key no row has (`No Document '…' in Shelf.files`), SQLAlchemy's `is not a valid ID.` and `is not an ISO 8601 datetime.` on filters, an upsert's `No Post matches {'title': '…'} and no create was sent`, and the MCP stored-operation tools' `has no arguments named [...]` came back at full length, and Strawberry logged each at ERROR on every request. Messages now quote at most 40 characters of a value and name at most 5 values.
- **The regex guard let through patterns it could not read, and repeats it did not count.** `(?c)(a+)+$`, `(?<n>a+)+$` and `\p{L}+\p{L}+!` raised `re.error` in the guard and went to the database, which reads them in its own dialect. Nine `(?=a{99})` in `(?:…a)*b` took 200 ms on one 1,000-character value, and `(?:(?:(?:a{0}){99}){99}){99}b` took 3.2 s on one of 256. A pattern Python's `re` cannot parse, reads only with a warning, or that sets flags after its start is now refused; `iRegex` is analysed with the `(?i)` it runs under; lookarounds inside a repeat of variable count count toward the 100 characters; and a pattern may take at most 1,000 steps at one place in a value.
- **Tortoise's statement probe left its wrappers on the shared database client.** With the default `lazy_resolution="warn"`, each resolver on an ORM row swapped the default client's `execute_query` methods for counting ones and put back what it had found. Resolvers overlap (sibling rows of a list, two requests), so each overlap left a wrapper on the client for good: one list of about a thousand rows, or about a thousand ordinary requests, left every statement of every later request failing with `maximum recursion depth exceeded`, and a finished request's probe went on counting other requests' statements. The client now gets one counting hook, put on once, and a probe reads the difference.
- **An upsert `where` built before the type excluding a column kept it.** Declaring `@orm.type(User, exclude=["email"])` after a generated input that writes `email` was refused, but not after one whose upsert `where` matches on it, top-level or nested. So `where: {email: "b@example.com"}` told a caller whether a user with that email existed, and aimed an update or a link at the user it found. Such a type is now refused, naming the `where` input.
- **`lazy_resolution` kept a copy of the whole selection under each relation a row loaded unprefetched.** The report prints 160 characters of it, but each row recorded the full text, and a selection can repeat a field any number of times that runs once. It now records what a report prints.
- **Secret-looking names were matched as substrings.** `aes_key`, `db_pass`, `refresh_tok`, `authorization`, `master_seed` and `decryption_key` were offered in generated inputs, filters and orders. Names are now read by their words.
- **Importing pytest turned off `warn_missing_scope` in any process.** It is now turned off only by the option or by `STRAWBERRY_ORM_WARN_MISSING_SCOPE=0`.
- **Client values were kept in Python's warnings registry for the life of the process.** `__warningregistry__` keeps every distinct warning text. `lazy_resolution="warn"` quoted each load's path, alias and operation name; Django with `USE_TZ = True` warned about each naive datetime a client filtered by or wrote (an upsert's lookup and update, a ref list's update, a nested update), quoting it, and Tortoise about each naive datetime and time; and SQLAlchemy warned about a create taking the key of a row its session held, naming both rows by address. Each was a new entry, never freed, and the same unbounded text was logged on every request. Warnings now name only the type and field, a datetime or time is read in the default time zone before the ORM sees it, as the ORM itself would have read it, and a create taking a held row's key is refused, as the database would have refused it.
- **A cursor that did not decode was quoted back to the client and the log.** `after: "<base64 of 'c0' + 10 KB>"` failed with `['c0…'] expected to contain only 2 items`. It is now refused with `Argument 'after' contains a non-existing value.`
- **The MCP `graphql` tool's limits measured the text of an operation, not the work it made the server do.** A 900-value filter variable used under two aliases was converted 1,802 times, and a 9,999-value filter spread under 40 aliases held the event loop for 13 seconds; input defaults, directive arguments and literals under lists multiplied the same way. A 1 MB comment or string under the token limit was lexed on every parse, unused or duplicated fragments reached validation unmeasured, and a stopped mutation, a `MaxTokensLimiter` and every stored-operation call parsed the document again on the loop. Arguments are now counted against `max_variable_values` after coercion, wherever an alias or fragment repeats them and again as lists repeat them; an operation is refused past `GraphQLTool(max_length=)` characters (default 100,000) before it is parsed; unused and duplicated fragments are refused; and each call parses and validates once, in a worker thread.
- **A queries-only MCP `graphql` tool could run mutation resolvers, and `root_fields` applied one set of names to both root types.** `{ maintenance { reset } }` on a field typed as an interface `Mutation` implements ran `Mutation.reset`, and so did unions, lists of either and `node(id:)`. `root_fields=["posts"]` with `allow_mutations=True` also allowed `Mutation.posts`. A query that reached a mutation resolver was rerun with `execute_sync` when Django stopped it, running the mutation twice. The tool now runs operations on the schema it shows, names in `root_fields` apply per root type (`Query.posts`, `Mutation.publish`), and such a query is treated as a mutation and not rerun.
- **A row behind a second awaitable was served without its scope check.** The check awaited a resolver's value once at most, but graphql-core awaits what a field resolves to and then each awaitable item of a list. So a hidden row came back from an async resolver returning a coroutine or a DataLoader future unawaited, from a list or generator of loads or coroutines, from a subscription event shaped so, from a plain `@strawberry.type` attribute holding them, and through the MCP `graphql` tool. On Django every sync resolver of an `@orm.type` was one, since its worker thread hands back the awaitable it returned. A query behind two awaitables was read whole on Django and Tortoise, and a connection handed such rows counted them in `totalCount` and its cursors. Every value is now awaited until nothing is left to await, and every list read, before anything looks for rows in it.
- **Strawberry's `relay.connection` paged rows before holding them to scope.** Its edges, cursors, `pageInfo` and `totalCount` counted every row the resolver returned, and a hidden row came back as a null `node` at its own position, so `first: 1` with `after:` found where each one sat; a resolver returning a generator or an async iterable did the same once the library's own check had run. A connection a resolver builds itself or a type holds had the same flaw. `orm.schema()` now gives each `relay.connection` over rows the library's own paging, which holds them to scope first, over interfaces and unions too, and refuses a field that pages rows any other way.
- **A schema with none of the library's extensions served every row.** In a `strawberry.Schema` built without `orm.optimizer_extension()`, `scope_rows` was never applied to rows a resolver returned: `orm.field.lazy`, `orm.connection`, `relay.connection(ORMListConnection[...])` and plain `@strawberry.field` resolvers served drafts the scope hides, and connections counted them. The README listed only nested relations as unscoped there. A row of an `@orm.type` served in such a schema is now refused (`Cannot serve PostNode: no extension of this schema holds its rows to scope_rows. …`), whether the type decides its own `is_type_of` or not, an `orm.connection` holds its counts to its own backend's scope, and a `relay.connection` over rows is refused.
- **An upsert arm offered create and update whatever its projection named.** A relation that named only `update` and `upsert`, to link rows that exist, let a client create rows through `upsert.create`, and one limiting `create` to a field or two let `upsert.update` write every column; `create_node_input()` and `update_node_input()` built their roots the same way. Every input built from a projection now offers only the operations it names.
- **A many-to-many link row was written and deleted without asking its repo.** Linking a row into a list whose `through` table is a model of the app's own (a Django `through=` model, a class SQLAlchemy maps onto the `secondary` table, Tortoise's model of the through table) inserted a row of that model, and unlinking or deleting the member deleted its link rows, without asking that model's repo or `authorize`: a caller could add memberships the repo refuses and remove ones it cannot see. Each link row is now created, found and deleted through its repo and `authorize`, and a member whose link row is hidden reads as no member.
- **A write took a row off its old parent without asking the parent.** Moving a comment into another post's list took it from the post it was under, re-pointing a link let go of the row it held, and a one-to-one was taken from its holder, but the old parent was never read through its own repos: its scope, `can_unlink` and `authorize` were not asked, so a caller could take comments off a post it cannot see. The old parent, holder or previous target is now read through every repo governing it, refused as missing when one hides it, and asked to let the row go.
- **A row two sibling subclasses hold was written as a row of one.** A Django multi-table row, or a SQLAlchemy joined-table row without a discriminator, can be both a `Restaurant` and a `Bar`. A write reaching it through one sibling checked and authorized it as that sibling and its bases alone, so the other sibling's scope, `can_*` and `authorize` never saw it updated, unlinked, deleted or linked, and an upsert's match counted rows only the sibling's repo hides, telling the caller they exist. The siblings whose tables hold a row now scope it and are asked about every write, and an upsert's lookup counts only the rows they show.
- **SQLAlchemy: a concrete subclass's rows were checked against its base's table.** The library counted a concrete mapping's base among the models its rows belong to, though the base's table holds none of them, so a write re-read the row by its key in the base's table, where the key names another row or none: a hidden subclass row was written when the base's row passed, and a visible one refused when it did not. Reads applied the base type's scope by columns of a table the row is not in. A base now governs a subclass's rows only where its table holds them.
- **An upsert's "matches more than one" counted rows a base's repo hides.** Through `SealedDoc`, `where: {title: "dup"}` answered "matches more than one" exactly when a doc the docs repo hides was also titled `dup`, though the same doc looked up by its id read as missing: an oracle on the values of hidden rows. The lookup now counts only rows every repo governing them shows, at the root, in list items, in `apply_ref_list()` and on single links.
- **Writes could set the columns that pick a row or its model.** The columns of a Django composite primary key were offered by update inputs and could be set by an update hook, and Django saved the row over whichever row held the new key, or inserted one past `can_create`. A SQLAlchemy discriminator, a column a discriminator expression reads, and the foreign keys over them could be set through a base model's create or update, turning the row into a row of a subclass whose repo and `authorize` were never asked; reverse lists and one-to-ones held by such columns retyped or rekeyed the rows they wrote. None of these is offered now, and create data or an update naming one is refused.
- **Rows keyed by more than one column were told apart by one.** On SQLAlchemy, a relation loaded onto rows the app holds went to them by the first key column, so a row took another row's tags; a group matched its rows the same way and lost them; a subclass scoped apart from its base had its rows matched so, and a count through the base took in rows it hides. On Django, an upsert could link a foreign key in the key, and an update hook could move the row onto the key of a hidden row and overwrite it. Rows are now matched, grouped and looked up by every key column.
- **Two generated types of one name were merged, and the schema served whichever it met first.** A connection over a public node type served a staff type's nodes and columns, a ref list that takes no delete was published taking one, and a filter, order or group-by cut for one type was served where another that shows less should have been, so `object:` reached relations and columns that type hides. `orm.schema()` now refuses a schema in which two types of one name differ, naming the field and what differs.
- **SQLAlchemy: key sets over joined subclasses read the subclass's columns off a table joined to nothing.** A scope, a custom or relation filter, a relationship's `primaryjoin` and a write scope were reduced to the base table's key columns, so a criterion on a subclass column held for every key once one row met it: a negated custom filter kept the wrong rows, a reverse list unlinked or deleted a row outside its relation, and rows a resolver returned passed their scope. Where the set was left to correlate, a connection read through an alias counted hidden rows. Key sets now read the keys off the entity the select reads, and do not correlate.
- **SQLAlchemy: filters, orders and scopes added to an aliased root read an unjoined copy of the model's tables.** A resolver returning a select of `aliased(Post)`, of a subquery or CTE read as `Post`, of an aliased `with_polymorphic()`, or of a base of the type's model had the client's filters, orders, the type's `scope_rows` and custom filters written over the model's own tables, joined to nothing. A filter on a value only a hidden row held returned every visible row, an existence oracle on hidden rows, and an order by it ranked them. Such a statement is now read as a select of its class, keeping its rows, order, limit and offset.
- **A write decided on rows read from a replica.** With a router sending reads to a replica (a Django `DATABASE_ROUTERS` entry whose `db_for_read` returns `"replica"`, a Tortoise router, or an SQLAlchemy session whose `get_bind()` sends selects to another engine), every read a write made went there, while its writes went to the primary. That covered the row an upsert matched, a nested item, a ref list's ids, membership and link rows, each repo's `scope_query`, and the queries hooks and `authorize` make. With the replica behind, Ann's update of a doc the primary had since given to Bob passed `DocRepo.scope_query` and was saved over Bob's row, and a grant revoked on the primary still let `can_update` through. An unlink that found no link row on the replica deleted Bob's link row on the primary without asking its repo. On Django, a parent a resolver had read from the replica also sent a write's link-row lookups, cascade collection and constraint checks to the replica. While a write runs, Django and Tortoise now send every read it makes where it writes. On SQLAlchemy, a write is refused with `TypeError` on a session that would read any model it binds from another database than it writes it to.
- **A subclass's type with a `scope_rows` of its own read past its base type's.** A `Contract` that is a Django proxy or multi-table child of `Document`, or a single-table or joined-table SQLAlchemy subclass, is a `Document` row, and a write asks `DocRepo` about it. But a `ContractType` defining its own `scope_rows` stood in for `DocumentType`'s on every read through it: its list, a relation to contracts, a connection's rows and `totalCount`, `node(id:)` and a filter through a relation to contracts showed and counted contracts `DocumentType.scope_rows` hides, another tenant's included. A row of a subclass of such a subclass likewise skipped the middle type's scope. A row is now held to the scope of each type over a model whose table holds it, however it is read. On Tortoise and for a concrete SQLAlchemy mapping, whose rows are in a table of their own, a subclass's type still answers for them alone.

- **A `strawberry.cast` made outside an execution no longer types the row inside one.** Cast in the resolver.

Rows of a type an `is_type_of` decides load each shared relation with the rows all candidate types' `scope=` allow.

On Django from async code and on SQLAlchemy with `offload_sync_session`, such resolvers run on the ORM's worker thread. A resolver raises `RuntimeError` if other loads keep replacing its relations, or, on SQLAlchemy, if a relation holds unflushed changes.

- **`authorize=` is called once for each model a row belongs to, base first**, each repo's `can_*` is asked for each model whose repo differs, and a write through a subclass looks the row up through each base repo's `scope_query`.
- **A row a write updates is saved with only what the write set.** On Django the default `_save` passes `update_fields` for a row a write read, so a model `save()` override or `pre_save` receiver must add a column it sets to them, and a value changed in place is not saved. Upsert ops' `save` takes the names the write set.

Django multi-table creates use `save(force_insert=(models.Model,))`, and on Django 4.2 a child create that sets one of those keys is refused.
- **Batching declines queries holding state it cannot compare**, and rows from a batched related-manager read load their parent instead of sharing it.
- **Arguments a field extension adds are subject to tags**, and one it adds hidden without a default fails the build.

- **Regex lookups no longer match values longer than `max_regex_text_length`** (bytes on MySQL); `not` keeps them. SQLAlchemy `iRegex` ignores case on SQLite, and `for_tortoise(enable_regex_filters=True)` raises `ValueError`, as Tortoise has no regex lookup.
- **A filter whose values add up to more than `max_filter_value_length` characters, each reference counted, is refused**, as is a request whose filters do.
- **Messages quoting a client's value cut it to 40 characters** (`'xxxx…'… is not a valid id`), and the MCP tools name at most 5 unknown arguments.
- **`secretary`, `hashtag`, `badminton` and `tokenizer_name` are no longer treated as sensitive.**
- **Test suites must turn off the missing-scope warning explicitly.**
- **`lazy_resolution="warn"` emits one `UserWarning` per finding** naming only the type and field; the logged and raised report clips paths to 160 characters and lists at most 8 findings.
- **Naive datetimes and times a client sends are read in the default time zone** before Django or Tortoise sees them, as those ORMs read them with time zones on, and an SQLAlchemy create taking the key of a row its session holds raises `The database refused the write`.
- **`lazy_resolution` reports name an aliased field by its alias, and a field inside a fragment by its path**, where they fell back to a dotted path.
- **A type excluding a column an earlier upsert `where` matches on is refused** with "… can still match rows on them, so a caller can test values they cannot read".
- **An undecodable `after`/`before` cursor is refused** with `Argument '<name>' contains a non-existing value.`
- **The MCP variable budget bounds expanded, coerced arguments, defaults included**; unused and duplicated fragments are refused; a root type narrowed out of an interface no longer implements it in `graphql_schema`; with `allow_mutations=True`, a bare `root_fields` name both roots have is refused.
- **A list field's iterable is read into a list, and its awaitable items awaited together**, before scope checks run; an item that raises keeps its error in its place.
- **`orm.schema()` pages `relay.connection` fields over rows itself**, on a copy of the field for that schema, and refuses a resolver that builds its own connection over rows, a type holding one, or a paging extension other than Strawberry's.
- **A schema built with `strawberry.Schema` must give it `orm.optimizer_extension()` to serve rows of an `@orm.type`.** Without it, each such row is refused, as is a `relay.connection` over them.
- **A projection naming any operation offers only those, in every arm**: an upsert offers `create` only with `_meta.create` and `update` only with `_meta.update`, an upsert without `update` behaves as `onMatch: "IGNORE"`, and the writer refuses a create its input does not offer. A projection naming none still offers `create` and `update`.
- **Generated inputs leave out the columns of a Django composite key, SQLAlchemy discriminators and the columns and links that choose a row's model**, and `exclude_pk=False` brings back keys alone. Create data naming a model-choosing attribute is refused after `on_before_create`, an update setting a key column is refused, and a one-to-one held by a key column is not offered.
- **An id cannot name a SQLAlchemy row keyed by more than one column.**

A hidden replaced target that `onReplace` or an orphan cascade would delete now refuses the write rather than being unlinked and left in place. Backends gain `governs(model, row_class)` and `classes_holding(model)`; SQLAlchemy's `models_inherited` stops at a concrete mapping, and `AbstractRepo._get` reads a composite key.

A filter, order or group-by built again after that of a model it relates to differs from the first, so build one direction or show the relation.

A select of a model the type neither inherits nor is inherited by raises `TypeError`.
- **A write's reads go where it writes.** On Django and Tortoise, each write puts a router of the library's own first among the app's routers, if there are any. While `is_writing()` is true, that router answers `db_for_read` with the routers' `db_for_write`. A query naming its database itself (`.using()`, `using_db=`) still reads there. A Django write finds the database a row is written to as `save()` does, with `router.db_for_write(model, instance=row)`, not the database the row was read from. On SQLAlchemy, a write is refused with `TypeError` if the session's `get_bind()` answers a select of any model it binds, in the written model's registry, with another bind than an update of that model's table. Such a session must route by `is_writing()` too.

### Fixed

- **SQLAlchemy: every delete failed in a registry holding a class mapped onto a select, or an `AbstractConcreteBase`.** Finding the rows a delete cascades to read each mapping's table, and such a mapping has none, so deletes and unlinks through a link model of the app's own raised `AttributeError`. Such mappings are now skipped; their rows are read through the classes mapping their tables.

## 0.34.0

### Security

- **Repeating a fragment spread made the optimizer's work exponential in a query's depth.** A query of about 150 tokens that spread one fragment 12 times at each of 6 levels (`fragment U on UserType { posts { author { ...V ...V ...V … } } }`) held the event loop for 3–5 seconds of planning on every backend, and an `ORMListConnection` took as long with the optimizer off, where graphql-core ran the query in milliseconds. A fragment is now expanded once wherever it is spread in one selection, as graphql-core does, and the fields one relation is selected under, aliases included, are planned together, so planning costs what the query's text does.
- **A field typed as a model's type that returned a query over a subclass skipped the subclass type's `scope_rows`.** With `MemoType` over a Django proxy or multi-table child of `Document` (or a Tortoise model inheriting it, or a non-polymorphic SQLAlchemy subclass), an `orm.field.lazy(filters=…)`, an `@orm.field.eager()` typed `list[DocumentType]` or an `orm.connection.lazy` over `DocumentType` that returned `Memo.objects.all()` listed and counted a memo `MemoType.scope_rows` hides. Such reads now apply the subclass type's scope as well as the field type's.
- **Django: a multi-table child row with a repo of its own was written by the base model's repo when the write named the base, and so was a SQLAlchemy joined-table subclass mapped without a discriminator.** With `repos={Doc: DocRepo, SealedDoc: SealedDocRepo}`, `upsert(where: {id: 2}, update: {title: "x"})` through `Doc`, or `{delete: {id: 2}}` in `Folder.docs`, loaded row 2 as a plain `Doc`, so `SealedDocRepo`'s `scope_query`, `can_*`, hooks and `_delete` were never asked, and the match on `where` counted sealed rows that repo hides. A write through the base now looks for the row in each such subclass's table and reads it again through the deepest one holding it, the match on `where` is narrowed by each subclass repo's `scope_query`, and a row two unrelated subclasses both hold counts as no row. A Django proxy shares its base's table with nothing to tell its rows apart, so its repo governs only inputs built on the proxy.
- **On Django, `orm.apply_ref_list()` opened its transaction on the database the parent was read from.** With a primary/replica router, a parent read from `replica` was written on `default` outside the transaction, so when `can_link` refused `spam`, the `fine` written before it stayed. The transaction now runs on the router's write database, as `orm.apply_upsert()`'s did. On Tortoise, both ran on the model's default connection rather than the one its router writes to, with the same result; `in_transaction()` now opens on the routed write connection.
- **The regex guard let through patterns that backtrack for cubic time.** It never compared a possessive repeat or atomic group with the repeats still open, so `\w*\d*+!` took 3.3 s on 1,600 digits, and it tested overlap only on a sample of characters, so `\w*[^\x00-\u4e00]*!` passed although both sets match CJK letters. It now compares exact code-point sets, reading `\d`, `\s` and `\w` as `re.ASCII` reads them where it is on, and letters with every case `re` matches them to (`İ` and `i`, the Kelvin sign and `k`). A possessive repeat that overlaps an open repeat is refused, and counted repeats an open repeat can also match may read at most 100 characters in all, so `.*x{500}y` is refused.
- **The MCP `graphql` tool had no limit on how many fields an operation selects.** Aliases spread through fragments that spread each other multiply: a 220-token operation with three aliases at each of eight levels selected 16,402 fields, under every other limit. An operation may now select at most `GraphQLTool(max_fields=)` fields (default 1,000), counting each alias and each fragment wherever it is spread.
- **SQLAlchemy: an `on=` view rebuilt its relation's join from one key column, so it could list rows the relation does not.** `orm.field.eager(on="open_tasks")` over a relation whose `primaryjoin` adds `Task.done == False` listed finished tasks, a view of a to-one relation (`on="author"` on a book) looked up the author whose id equals the book's id, and a relation joined on another column (`Book.author_code`) was matched against the parent's primary key. An `on=` view is now served only for a to-many relation joined on the parent's primary key alone, and any other is refused when the type is defined.
- **SQLAlchemy: ordering a list through a to-many relation read every row when the statement carried loader options.** `posts(order: [{object: {tags: {field: {name: ASC}}}}], first: 2)` under a `scope_rows` adding `with_loader_criteria`, or a resolver using `contains_eager`, fetched every post with no `LIMIT`, and a root list under `default_query_limit` came back null. The database now cuts the page: `with_loader_criteria` goes onto the numbered page, and with other loader options the statement is narrowed to the entities on the page.
- **SQLAlchemy: relation batching merged sibling statements that differed only in their options.** One parent's statement used `.execution_options(show_drafts=True)` or a `UserDefinedOption`, which a `do_orm_execute` hook reads to widen its rows, and the other parents' statements, with the same SQL, ran as part of it, so Bob saw drafts his statement never asked for. Statements now batch together only when their execution and loader options match too.
- **Rows a resolver returned as a list of lists were not scoped.** A `list[list[PostType]]` field returning `[[hello, draft], [rust]]` (as lists, tuples, generators or async iterables) showed a draft that `PostType.scope_rows` hides, and `orm.optimize()` let it through. Rows are now checked at every level, and a hidden row is dropped from its inner list.
- **`on_after_*` hooks ran before the database had accepted the write.** On SQLAlchemy a link is written only as the savepoint is released, so a tag the database refused had already been announced. On Django, foreign keys on SQLite and PostgreSQL are checked at commit, so a comment with `author_id: 999`, or a delete that left a `DO_NOTHING` row's key behind, ran its hooks first, and inside `ATOMIC_REQUESTS` was refused only after the resolver returned. SQLAlchemy now flushes, and Django checks the foreign keys of the tables written, before any hook runs, and a refusal there runs none of them.
- **`authorize=` was told the caller's spelling of a key, before the row was read.** On a text key the database matches regardless of case (SQLite `NOCASE`, a MySQL `_ci` collation), `{delete: {id: "SECRET"}}` reached `authorize` as `"SECRET"`, so a callback that refuses `"secret"` let the delete of row `secret` through, and since it was asked about rows the repo hides and rows that do not exist, its answer could tell them apart. `authorize` is now asked once the row is read, with the key the row stores, and never about a hidden or missing row, which fails as a missing one does.
- **SQLAlchemy: `orm.input()` and `orm.partial()` offered a foreign key column whose relationship is declared only on the other model.** With `User.posts = relationship()` and no `Post.author`, `orm.input(Post)` offered `author_id`, which `orm.apply_ref_list()` wrote as a plain value past the user repo's `scope_query` and `can_link`. Every foreign key column is now left out unless `include=` names it; a joined-inheritance child keeps its own key.
- **SQLAlchemy: a flush the unit of work refused reached the client in SQLAlchemy's words.** Re-pointing a shared-key one-to-one came back as `Dependency rule on column 'internal_accounts_v3.id' tried to blank-out primary key column 'internal_profiles_v3.account_ref' …`, and a lost update as `UPDATE statement on table 'internal_members' expected to update 1 row(s); 0 were matched.` Any SQLAlchemy error, and an `AssertionError` SQLAlchemy raises itself, is now `The database refused the write` (`Invalid filter expression` on reads), with the original as the cause. An `assert` in the app's own hooks is left alone, and a pool timeout is `Database connection failed`.
- **An integer id past 64 bits reached the driver.** `{update: {id: "99999999999999999999999"}}` came back as `Python int too large to convert to SQLite INTEGER` on SQLAlchemy and Tortoise, and on Django matched nothing. It is now refused like `"abc"`, as not a valid id. A value the driver cannot bind is `The database refused the write` (`Invalid filter expression` when read) on every backend, and so is a Tortoise `ValidationError` on a write, whose message named the field and repeated the value.
- **MCP tools took variables of any size.** A `graphql` call with a 2.8 MB `inList` of integers, or with thousands of filter objects, was coerced by GraphQL on the event loop before any limit applied, and stored operation tools took the same. A call's variables may now hold at most `mcp_server(max_variable_values=)` values (default 10,000), counting each object, list and scalar, and nest at most 100 levels deep. They are measured in a worker thread before they are coerced.
- **The MCP `graphql` tool's errors suggested names from a schema it keeps back.** With `schema_tool=False`, on a schema that refuses introspection, or with `disable_field_suggestions=True`, `{ documents { internalReviewerNote } }` was answered "Did you mean 'internalReviewerNotes'?", and an enum value or input field one letter off, inline or in a variable, was answered with the real one. These errors now suggest no names.
- **An MCP mutation stopped by `SynchronousOnlyOperation` did not say what had already run.** Without `sync=True`, `mutation { chargeCard writeReceipt }` charged the card, stopped in `writeReceipt`, and answered only "a mutation is not run a second time", so a client that tried again charged the card twice. The result now comes back with its errors and names the root field Django stopped and those that ran before it: "stopped writeReceipt, after chargeCard had run".
- **MCP `root_fields` and queries-only tools did not narrow a root type reached through a field.** A payload's `query: Query` field returned the whole query type, so `{ payload { query { hidden } } }` ran a root field `root_fields` leaves out, and a query field returning `Mutation` let a queries-only `graphql` tool run mutations. Such fields now return the narrowed root type, and a field returning a root type the tool leaves out is left out too.
- **`GraphQLTool(descriptions=False)` kept deprecation reasons.** `@deprecated(reason: "Internal: read by the billing cron")` reached every MCP client in `graphql_schema`. Reasons are now left out along with the descriptions, and `@deprecated` itself stays.
- **Write errors named the Python model class.** `No WaFile 'gone' in WaShelf.files`, `'abc' is not a valid Tag id` and `authorize denied the delete operation on Contract` showed class names that can differ from the schema's types. They now name the GraphQL type the client sees (`No Document 'gone' in Bookcase.files`), and only "row" or nothing when the model has no type or several (`'abc' is not a valid id`).
- **Django: a `GenericForeignKey`'s content type stayed writable after its `object_id` was taken out of inputs.** A projection naming `kind` offered it in node and upsert inputs, so an update could re-point a remark from `Post` 7 to `Invoice` 7, a row no repo was asked about. The content type's column is now left out of generated inputs, `where`, `orm.input()` and `orm.partial()` with the `object_id`, and a projection naming it raises `ValueError`.
- **A `using=` path through a relation the schema does not show took the `scope=` of whichever type over the related model was registered first.** With `StaffUserType` (plain `posts`) registered before `PublicUserType` (`posts` with `scope=published_only`), `@orm.field.lazy(using=["author.posts"])` on a `PostType` without an `author` field loaded the author's drafts. Where the type cannot be told, each relation now applies every type's `scope=`, as filters past an `object:` hop already do.
- **`mcp_server()` built a server that can change data without saying it had no authentication.** It now warns when a mutation tool, or a `graphql` tool with `allow_mutations=True`, is served without `auth=`.
- **The test workflows left the checkout's token in `.git/config`** for every later step, dependency installs included. They now check out with `persist-credentials: false`, as the release workflow does, and `.gitignore` covers local `.cursor/` and `.mcp.json` files.
- **`README.md` documents two more exposures left to the app.** Strawberry's `QueryDepthLimiter` and `MaxAliasesLimiter` walk a fragment again wherever it is spread, so a short operation can hold them for seconds before the optimizer's own walk is reached; and the MCP server's DNS rebinding protection holds only for `localhost` hosts unless `TransportSecuritySettings` names the server's own.

Async writes now await it, and a sync write raises `TypeError` instead. A result is read as a bool: `False` and `None` deny, and a truthy value other than `True` still allows but emits a `DeprecationWarning`.
- **An upsert miss wrote `where` fields that `create` does not allow.** A miss seeds the new row from `where`, so with `where: True` a caller could set any offered column on the new row, past the `_meta.create` allowlist (`is_published` on a post whose `create` lists only `title` and `body`). Sending a `where` field other than `id` that `create` does not offer, together with `create`, is now a validation error.
- **Node mutation inputs wrote columns their type excludes.** Inputs from `orm.mutations` ignored `@orm.type(..., exclude=[...])`, so a column hidden from reads stayed writable through `create_node_input`, `update_node_input` and `upsert_node_input`, unlike through `orm.input()`. Generated inputs now leave excluded columns out. Naming one in a `_meta` projection raises `ValueError`, and so does declaring the type after an input that already writes the column.
- **Re-pointing a link skipped `can_link` and `can_unlink`.** A single link pointed at an existing row, and an `update` item that took a row from another parent's list, asked neither whether the row could be linked nor whether it could leave where it was. A caller could move another user's comment onto their own post, or point a post at another author. Now `can_link` is asked for an existing target, `can_unlink` for the row a re-pointed link replaces, and `can_unlink` of the old parent when a row moves between lists.
- **A refused ref list stayed partly written.** A plain `orm.ref` list was written item by item, so a denial on the third item left the first two in place. Every list is now one unit of work, like an upsert: a savepoint on SQLAlchemy, `transaction.atomic()` on Django and `in_transaction()` on Tortoise.
- **A `MutationPolicy` passed with `repos=` never ran.** `policy=` was silently dropped whenever `repos=` was also given, so none of its checks applied to any model. Passing both now raises `ValueError`.
- **A ref-list delete bypassed the repo's delete on SQLAlchemy and Tortoise.** `{delete: {id}}` deleted the row directly, so a soft-delete `_delete` override was skipped and the row was gone for good. It goes through the repo now, as it did on Django.
- **A connection could be made to read a whole table.** `first` and `last` were capped at `max_results`, but `before` alone paged up to its cursor however far that was, `last: 0` returned every row after the cursor, and a forged cursor before the first row (`after: "arrayconnection:-5000"`) read every row with no `LIMIT` to slice them in Python. `before` alone now reads one page from the start, as no arguments do. `last: 0` returns an empty page at the end of the result. A cursor before the first row is refused with `Argument 'after' cannot point before the first item.`
- **A group's `items(last: 0)` returned the rows read for the group.** The `last: 0` fix above did not reach a connection's `groups { items }`, so each group answered with its first page. It is now an empty page at the end, as on the connection, read from at most one row per group. A `last` written in the query was also ignored when each group's rows were read, while one passed as a variable was not; both now read the same rows.
- **`groupBy` answered with any number of groups.** Grouping by a column with many values, such as `id`, built a group per value even for `first: 1`, and an `objects:` key held every related row of its group. A connection now refuses more than `max_groups` groups (default 100), and an `objects:` key holding more than `max_group_key_rows` related rows (default 100). Either one is an error, not a truncated answer.
- **An `objects:` group key was built whole before `max_group_key_rows` refused it.** The database put every related row of each row into its key, 3,000 tags' worth for a post with 3,000 tags, and only then was the key counted. Each key now reads at most one row more than `max_group_key_rows`, enough to tell that it is too big. Ordering by `objects:` still reads every related row, as the order of the whole set depends on them.
- **On SQLAlchemy, a refused write reached the client with its SQL and the row's values.** The statements `orm.apply_upsert()` and `orm.apply_ref_list()` run were not covered: a unique email in an upsert's `create` returned the `INSERT` with every bound value, those of columns the API leaves out included, and a value the column type refuses in its `where` returned the lookup's `SELECT`. Writes, sync and async, now report `The database refused the write`, or `Database connection failed`, with the original kept as the cause.
- **The Security section did not say writes ignore `scope_rows`.** A model with `scope_rows` but no repo could still be updated, linked or re-pointed by ID through `orm.apply_upsert()` and `orm.apply_ref_list()`: taking another user's post into your own list made it yours, and an upsert's match told whether a hidden row held the values in `where`. The responsibility table now lists write access, and [Writes do not apply `scope_rows`](README.md#writes-do-not-apply-scope_rows) says what repo a writable model needs.
- **On Tortoise, a `@group_field` method was handed every row of the model.** Its `query` argument was `Model.all()`, not the rows grouped, so a key it built from a subquery over `query` read rows `scope_rows` hides. It is now the scoped query being grouped, as on Django and SQLAlchemy.
- **On SQLAlchemy, requests sharing a session read each other's relations.** With one `AsyncSession`, or a sync `Session` with `offload_sync_session=True`, used by concurrent requests, a load marked as read under its scope whatever relation became loaded while it ran, including one another request's load filled, and a mark stood after another load replaced the relation. A guest read drafts an admin's request loaded on the same `User` rows, and an admin missed drafts a guest's had hidden. A load now marks nothing if another request ran a statement on the session meanwhile, and a mark lapses once the relation holds something else; either way the relation is read again under the reader's scope. A row checked against `scope_rows` while another request marked it is no longer dropped.
- **A row returned for an interface or union took the first type over its model.** A resolver typed `relay.Node`, or any interface or union, that returned a `User` row as it was gave it whichever type over `User` came first: with a `StaffUser` showing `email` ahead of a `PublicUser` that excludes it, `{ feed { ... on StaffUser { email } } }` returned every email. A row two types in the schema read is now refused, with an error asking for `strawberry.cast(TheType, row)`; a type with its own `is_type_of` still decides for itself. A row of a model subclass takes the type over its nearest class rather than the first declared.
- **A relay `node()` list told a row `scope_rows` hides from one that does not exist.** `nodes(ids: [...])` answers each ID in its place and an ID with no row as `null`, but a hidden row was dropped from the list, so the answers after it moved up, and comparing two lists showed which IDs named hidden rows. A hidden row is now answered `null` in its place, as a missing one is, and a required one fails the field the same way.
- **`authorize=` on `orm.apply_ref_list()` saw the ID as the client sent it.** For an `update`, `unlink` or `delete` item it was given the raw string, so a callback denying key `1` let `"01"`, or the row's Relay global ID, through to the write. It is now given the primary key the item names, as the upsert paths already did.
- **`onReplace: DELETE` deleted a row the caller could not see.** Re-pointing a single link deleted the row it replaced after asking only `can_unlink` and `can_delete`: the row was read off the parent, not through the related repo, so its `scope_query` never applied, and `authorize` was not asked about the delete. Re-pointing a post's author away from another tenant's user deleted that user. The replaced row is now read again through the repo and deleted only if it is visible and `authorize` allows `"delete"`; otherwise it is disconnected and left in place, and the response is the same either way.
- **The MCP `graphql` tool could be stalled by a short operation.** Its depth check walked a fragment once for every path to it, so fragments that each spread the next twice took twice as long per link: about 800 characters cost a second, and 1,200 twenty minutes, on the event loop, before any limiter extension ran. Each fragment is now measured once, the check runs in a worker thread, and the operation is refused past `GraphQLTool(max_tokens=2_000)` as it is parsed.
- **`exclude=` did not hide a column a base Strawberry type declares.** `@orm.type(User, exclude=["ssn"])` on a class inheriting `ssn: str` from a `@strawberry.type` or interface still showed `ssn` to every caller: Strawberry copies a base's fields into each subclass. Naming such a field in `exclude=` now raises `ValueError`. To keep a shown column out of filters and orders only, pass `exclude=` to `orm.filter()` and `orm.order()`, as before.
- **A column an interface guards with a field extension could be filtered, sorted and grouped by.** `email: str = strawberry.field(extensions=[PermissionExtension(...)])` on a Strawberry interface an `@orm.type` inherits refused `email` to the caller, yet `filter: {field: {email: {startsWith: "bob"}}}`, `order` and `groupBy` on it worked, recovering the value a prefix at a time. An inherited field with extensions now stays out of the inputs, as one with permission classes did.
- **A relation connection guarded by a field extension could still be filtered through.** With `posts: ORMListConnection[PostNode] = orm.connection.eager(extensions=[PermissionExtension(...)])`, a caller refused `posts` could still ask `users(filter: {object: {posts: {field: {title: {exact: "Draft Post"}}}}})` and learn who wrote it. A connection given `extensions=` no longer opens its relation to `object:` filters, as an own field with extensions already did not.
- **On Django and Tortoise, a refused write reached the client with the table and column.** A unique tag name created through `orm.apply_ref_list()` returned `UNIQUE constraint failed: tag.name`, and on PostgreSQL the error's detail carries the row's values. `orm.apply_upsert()` and `orm.apply_ref_list()` now report `The database refused the write` (Tortoise: `Database connection failed` when the connection is lost), as SQLAlchemy does. Code that caught `IntegrityError` around them should catch `ValueError` and read its `__cause__`.
- **`orm.field.eager()` given a scope dropped its `permission_classes`.** `orm.field.eager(scope=published, permission_classes=[IsStaff])`, or the scope passed positionally, returned the rows to anyone: the permission was never checked. `compute=` and `disable_optimization=` were dropped the same way. All three now apply alongside the scope.
- **A relation connection's `scope=` was ignored.** `posts: ORMListConnection[PostNode] = orm.connection.eager(scope=published)` on a type returned the rows the scope hides, in its edges, `totalCount`, aggregates and groups, on every backend. The scope narrows the relation as an `orm.field.eager(scope=...)` on it does.
- **SQLAlchemy: a row keyed by more than one column was matched by the first.** `groupBy`, a filter through a scoped relation and a custom filter under `not:`, `any:`, `oneOf:` or `object:` match rows by key against the rows they keep, and compared only the first key column. A row the type's `scope_rows` hid was counted in a group, and matched a filter, when it shared that column with a row it showed, and grouping across a to-many relation counted each row under the related values of every row sharing it. The whole key is compared.
- **`order` and `groupBy` took any number of entries.** 5,000 entries made 5,000 `ORDER BY` terms. A list longer than `max_order_entries` or `max_group_by_entries` (default 10 each) is refused before any SQL is built.
- **On SQLAlchemy, a page ordered through a to-many relation read every joined row.** `order: [{object: {tags: …}}]` repeats a row once per related row, so the page was read whole and sliced in Python: `first: 1` read 12,000 rows. The page is now cut in SQL, each row counted once at its first appearance, as `.unique()` reads it. A join the resolver already cut with a `LIMIT` or `OFFSET` is still read whole, since that limit counts joined rows.
- **On SQLAlchemy, a database error reached the client with its SQL.** Only `OperationalError` and `ProgrammingError` on reads were replaced. A value the column type refused, such as a malformed UUID in `filter: {field: {id: {exact: "not-a-uuid"}}}`, returned the statement for edges, `totalCount`, aggregates and groups: the table name, columns the API leaves out and the `scope_rows` predicate, and on PostgreSQL the bound parameters. Every statement the library runs, including eager loads, counts and relation counts, sync, async and offloaded, now reports `Invalid filter expression`, or `Database connection failed` when the connection is lost. The original is kept as the exception's cause, for the server log.
- **The MCP `graphql` tool answered `__schema` and `__type`.** `root_fields` hid fields, types and mutations from `graphql_schema`, but an operation asking for `__schema` or `__type` was answered from the whole schema and listed them all. Such an operation is now refused, with or without `root_fields`; `graphql_schema` describes what the tool may use. `__typename` still works.
- **The SQLAlchemy filter helpers defaulted to allowing regex.** `_build_lookup_clauses`, `_build_sa_field_clause`, `_build_sa_filter` and their callers took `enable_regex=True` unless told otherwise. Every caller passed the configured value, so nothing reached them, but a new caller would have enabled regex without `enable_regex_filters`. They default to `False` now.
- **The release workflow ran actions by tag and put the tag name in its script.** Every action in the workflows is pinned to a commit SHA, and `github.ref_name` reaches the release script through `env:` rather than being written into it. The release job runs in the `pypi` environment, so its protection rules gate the PyPI upload.
- **`not:` over a to-many relation tested hidden related rows.** On Django, `posts(filter: {not: {object: {comments: {field: {body: {startsWith: "the password is h"}}}}}})` dropped a post when a comment the caller cannot read matched, so hidden values could be read a character at a time. On Tortoise, a hidden related row was enough to drop a parent, and a parent with no related rows was dropped too. Through a to-many relation, `object:` is now one condition per parent, "a readable related row matches" (an `EXISTS` on Django, one subquery of the matching parents on Tortoise, as SQLAlchemy already did), and `not:` negates it whole.
- **A `@filter_field` through `object:` ran on the parent's query, over every row.** `posts(filter: {object: {author: {search: "bob@secret"}}})` ran `search` on the posts query, uncorrelated and unscoped, so all posts or none came back: a yes/no question about users the caller cannot read. Under `not:`, a custom filter was applied as if `not:` were absent, and in `any:` it narrowed the whole query instead of adding an alternative. Anywhere but the top of the filter (alone or in a top-level `all:`), a custom filter is now called on a fresh query over its own model, its rows are matched by primary key, and that condition is negated, combined or tested on the related row as its place says.
- **Root filters and `groupBy` used the edge `scope=` of the model's first-registered type.** With an admin type and a public type over one model, the public type's `scope=` on a relation was skipped when the admin type was registered first, so grouping or filtering through that relation read the rows it hides. The `scope=` now comes from the type the field returns. Where that cannot be told, as past an `object:` hop, every type over the model contributes its `scope=`, and only rows all of them allow are reached.
- **Filter limits held for each list, not for the filter.** A variable can be referenced any number of times, so a 10 KB request repeating one 500-value `inList` a couple of thousand times built a statement with a million bind parameters, every list within its limit. `max_filter_branches` and `max_in_list_size` now count every entry and every value across one filter argument, each reference to a variable included, and a filter over either is refused before any SQL is built.
- **A connection over a relation could sort by a scoped type's columns.** `comments(first: 10, order: [{object: {author: {field: {name: ASC}}}}])` was refused on a root connection but, on a relation connection, ranked comments by authors the caller cannot read. Connection ordering now runs the same check as every other order, and the check `orm.schema()` runs at build time covers the order of every type over a model, not only the last one registered.
- **The foreign-key shortcut compared any integer column with the foreign key.** `object: {author: {field: {age: {exact: 2}}}}` matched the posts whose `author_id` is 2, revealing foreign-key values and returning the wrong rows. The shortcut is taken only for the related model's primary key through a forward foreign key now, and any other column is compared on the related row.
- **Tortoise errors listed every column of the model.** A filter by key through a reverse relation (`object: {posts: {field: {id: {exact: 1}}}}`) was built as a `posts_id` column that does not exist, and Tortoise's error, which lists the model's columns, hidden ones included, reached the client. Reverse and many-to-many relations are filtered on the related rows now, and a filter Tortoise cannot resolve is refused with "Invalid filter expression".
- **`max_filter_depth` did not count levels under the foreign-key shortcut.** `object: {author: {not: {not: …}}}` was accepted as deep as graphql-core allows. Those levels count now.
- **Reference lookups read numeric-looking IDs as integers.** `{exact: "00123"}` on a text key was compared as `123`, so it missed its row and matched another or nothing, and raised on PostgreSQL. An ID is matched as the key column holds it now: as given on Django and Tortoise, and on SQLAlchemy converted only for an integer or UUID column, where an ID that is not one is refused.
- **Selecting a relation of rows handed to `orm.optimize()` skipped their scope.** `orm.payload.query` and `orm.payload.mutation` resolvers returning instances, and a manual `orm.optimize(rows, info)`, loaded the selected relations onto them and marked them as prepared, which the row scope check trusted. `{ post(id: 2) { data { title author { name } } } }` returned a draft its type hides, though without `author` in the selection `data` was `null`. Instances are now checked against `scope_rows` before anything is loaded onto them, the rows it rejects are dropped, and only rows a scope check kept are marked.
- **Rows a resolver returned in anything but a list skipped `scope_rows`.** graphql-core reads any iterable for a list field, but only a single row or a `list` was checked, so a tuple, a generator, an async iterable or a SQLAlchemy `ScalarResult` (`session.scalars(stmt)` without `.all()`) returned every row the resolver read, with the optimizer on or off. Such a result is now read into a list and checked as a list is. Strings and mappings are left to graphql-core, which does not read them as lists.
- **A connection over the rows a resolver read counted the hidden ones.** When a connection's resolver returned rows rather than a query, `totalCount`, the cursors and the page included rows `scope_rows` hides, whose `node` then failed as a non-null error. The rows are now checked before they are counted or sliced.
- **Rows of a subclass skipped the scope of their base model's type (SQLAlchemy, Django).** The type over a model accepts rows of an inherited SQLAlchemy mapping, a Django proxy or a multi-table child, but the scope was looked up by the row's or query's own class, which had none, so `{ document(id: 4) { title } }` returned a `Contract` the `Document` type hides. The scope is now found through the classes a model inherits: a subclass's rows and queries are scoped by its base's type, unless a type over the subclass defines its own `scope_rows`.
- **On Django, a proxy or multi-table child row's relations skipped their `scope=`.** A relation's `scope=` was looked up by the type over the row's own class, which had none, so `posts` on `FeaturedUser` rows returned as `UserType` came back without the `scope=` that `UserType.posts` puts on it. A subclass row is now read by its base's types, and their `scope=` applies; when the type cannot be told, the `scope=` of every type over the row's class and the classes it inherits applies.
- **SQLAlchemy: a relation loaded with a scope that joins kept only its WHERE clause.** A nested relation, read for the selection or through `using=`, was loaded with the WHERE clause of the related type's `scope_rows` and its `scope=`, and the rest of the statement was dropped. A scope that joins, such as `select.join(Membership).where(Membership.user_id == me)`, then let through every row of a visible parent: `{ orgs { projects { name } } }` listed projects the root `projects` field hides. To-one and many-to-many relations had the same gap. A scope that is more than a `.where()` on the related table's own columns is now run whole, as a statement of its own per relation, keyed by the parents' join column.
- **SQLAlchemy: a scope's `with_loader_criteria` was lost wherever the scope ran inside another statement.** SQLAlchemy applies those criteria from the outermost statement only, and counts, aggregates, groups and their items, orders and groups by a relation's rows (`objects:`), filters through relations, and the check on rows a resolver returned all run the scope as a subquery. A filter through `author` matched users the `User` type hides, `totalCount` and aggregates counted hidden rows, and an `objects:` key listed hidden tags. The statement a scope runs inside now carries its `with_loader_criteria`.
- **A relation loaded for one field's `scope=` was trusted by another.** The mark saying a relation's cache was loaded with its scope did not say which `scope=`. With two types over one model, one reading `posts` unrestricted (through `using=`, say) and one through `orm.field.eager(scope=published)`, the second read the cache the first loaded on the same row: `{ stats { draftCount } user(id: 1) { posts { body } } }` returned a draft's body. The mark now records the `scope=` the relation was loaded for, and a field with another one reads the relation again. On SQLAlchemy, a relation one statement loads in two places under different scopes is not marked at all. All backends.

### Added

- **`max_groups`** (default 100) and **`max_group_key_rows`** (default 100) on every backend: the groups one connection may answer with, and the related rows one `objects:` key may hold.
- **`max_order_entries`** and **`max_group_by_entries`** (default 10 each) on every backend: the longest `order` and `groupBy` lists accepted.
- **`get_default_queryset(model, limited=False)`** on a backend reads every row of the model, without `default_query_limit`. `orm.get_default_queryset(Model)` still applies it.

### Changed

- **Projections no longer imply destructive operations.** A to-many relation in a `project=` without `_meta` used to offer `unlink` and `delete`, and a single link offered `onReplace: DELETE`, which deletes the row the link replaces. A relation now offers `create` and `update` until its `_meta` sets `unlink: True` or `delete: True`, and a re-pointed link only disconnects the row it replaces unless `onReplace` lists `"DELETE"`. A link with a single `onReplace` option is a `@oneOf` input with no `onReplace` field. This changes the generated schema for projections that relied on the defaults.
- **Plain `orm.ref` items go through the same writer as upserts on every backend.** An item naming more than one of `create`, `update`, `unlink` and `delete` raises `UpsertValidationError` before anything is written, where the first one used to be applied. A `delete` from a many-to-many list removes the row from the relation before deleting it, so a row a soft-delete repo keeps also leaves the list.
- **`apply_ref_list` validates every list**, not only lists with generated items, so a hand-built list is checked in full before its first write.
- **Paging diverges from Strawberry's `ListConnection` in three requests** that it answers by slicing a Python list: `before` without `first` or `last` reads one page (`max_results`, or `default_query_limit` when that is smaller) from the start, not every row up to the cursor. `last: 0` returns no edges, with `hasPreviousPage` true when rows follow the cursor. A cursor before the first row is an error, where Strawberry counted it from the end of the list.
- **`default_query_limit` caps each read, not the rows a connection pages through.** It cut the query a generated connection was built on, so `totalCount` stopped at the limit and no page went past it. Now a connection's page is at most `default_query_limit` rows, `first` and `last` included, and its default when neither is given, and every page is reachable. A generated root list (`users: list[UserType] = orm.field.eager()`) is cut to the limit after its filter, order and `scope_rows`. On Django it was cut first, so a `filter` or `order` on it failed with "Cannot filter a query once a slice has been taken." A nested relation list is not limited; cap the root it hangs from, or make it a connection.
- **SQLAlchemy: a join that repeats rows is paged in the database.** See the security note above. `README.md#connection-fields` lists what is still read whole.
- **Filter limits are totals.** `max_filter_branches` and `max_in_list_size` count across the whole filter argument, and `max_in_list_size` counts the two ends of a `range` too. A filter that ran with several lists each under the limit may now be refused. A custom filter's value is not counted; a `@filter_field` that takes a list should cap it.
- **A custom filter under `not:`, `any:`, `oneOf:` or `object:` gets a fresh query over its filter's model**, not the field's query, and its rows are matched by primary key. A `@filter_field` that relied on what the field's query was already narrowed or joined by sees only its own model there.
- **Each `object:` through a to-many relation is its own condition.** On Django and Tortoise, `all: [{object: {tags: A}}, {object: {tags: B}}]` matches a post with one tag matching `A` and another matching `B`, as on SQLAlchemy, rather than needing one tag to match both.
- **`orm.schema()` checks the order input of every type over a model**, so a schema with an earlier-registered type whose order reaches a scoped type now fails to build, as one with that type registered last already did.
- **`build_reference_object_filter_clause` and `filter_tree_uses_only_reference_lookups` take `key=`**, the related field the foreign key holds, and the first takes `max_depth=` and `depth=`.
- **`orm.optimize()` returns what its scope check kept.** It returned what it was given, with relations loaded. A list comes back as a copy without the rows `scope_rows` rejects, and a rejected single instance as `None`, so use the return value: `rows = orm.optimize(rows, info)`.
- **SQLAlchemy: a relation whose scope is more than a `.where()` on the related table's own columns** is read in a statement of its own, keyed by the parents' join column, rather than by a `selectinload`. Through an association table, one statement more reads the links. Such a scope on a relation that does not join on one column (a composite key, or a `primaryjoin` that says more than the key comparison) now raises a `ValueError` naming the relation, where it loaded rows the scope hides. Write that scope as a `.where()` on the related table's columns, or read the relation in a resolver of your own.
- **SQLAlchemy: an ordered scope on a many-to-many relation keeps its order**, through an association table on one key column, for it is read the same way. This lifts the 0.29.0 limit for those relations.
- **SQLAlchemy: a scope's `with_loader_criteria` applies to the whole statement the scope runs inside**, as it does to the statement the scope returns: every place its entity is read there. A relation's `scope=` that uses it on the model the outer statement reads, as on a relation from a model to itself, narrows the outer rows too.
- **A relation connection without `first` is read in one query for every parent.** `{ users { posts { … } } }` sent one query per user; it is windowed at the page the connection returns, `max_results` or `default_query_limit` when that is smaller, as `first` was. `first` above `default_query_limit` no longer reads past it either.

### Fixed

- **On Tortoise, a repo could not find a row whose key is not an integer.** `AbstractRepo._get_async` cast every key with `int()`, so an `update`, `unlink` or `delete` on a model keyed by a UUID matched nothing, and one keyed by a string raised `ValueError`. The key is now looked up as the model stores it.
- **A relation connection's `aggregates`, `groups` and `pageInfo { aggregates }` were lost when its page was windowed.** `posts(first: 10) { aggregates { count } }` answered `null` for every parent, and `pageInfo { aggregates }` raised. A connection that selects them is read one parent at a time, from the relation's own query.

## 0.30.0

### Security

Each of these let a request read rows its type's `scope_rows` hides, in 0.29.0.

- **A resolver named after a relation was trusted as the library's read of it.** A field named like a relation of its model, such as an app's own `@orm.field.lazy def posts(...)`, skipped the related type's `scope_rows`, so it returned every row its resolver found. Only the library's own relation resolvers and `on=` views are trusted now, whatever they are named. That also stops a view named in several words (`recent_posts`) being checked again a parent at a time.
- **A query `scope_rows` handed back unchanged was marked as scoped.** An admin's request, whose scope returns the query as it is, marked a query kept between requests (a module-level `select()` or queryset) as already scoped, and every later request read all its rows. Only a query the scope narrowed is marked now.
- **What one request learned about scoping was trusted by the next.** Rows, relation caches and queries stayed marked as scoped, so rows that outlive a request (cached by the app, or in a SQLAlchemy session shared by several requests) skipped `scope_rows` from then on. After an admin's request, the next user read the admin's rows and relations. A mark now holds only for the execution that made it, and each subscription event is an execution of its own.
- **Rows `scope_rows` rejected were removed from the resolver's own list.** The list a resolver returned was filtered in place, so a list the app keeps lost those rows for every later request, including those allowed to see them. They are dropped from a copy now.
- **Connection state was kept on `info.context`.** Groups and aggregates read the connection's query from there, by the field's path, so a server that shares one context object between requests could hand one request's query, and its scope, to another's. Wherever the optimizer extension runs, as under `orm.schema()`, the state is kept for the execution instead.

### Added

- **Ordering by the set of a to-many relation's rows.** `order: [{objects: {tags: {field: {name: ASC}}}}]` sorts each row by all of its visible related rows together, by the same value `objects:` grouping keys a group by. Rows with the same set sit together, so grouped by the set too, each group's edges are one run, its `items` follow the order, and groups are ranked by their least (or greatest) set. Naming the relation in several entries makes one set of all their columns. The entries must agree on the direction, and the nulls variants sort as plain `ASC`/`DESC`, since a row with no related rows has `[]`. The set is compared as JSON text: on SQLite that is byte order, which puts `[graphql, python]` before `[graphql]` and `[]` last. On PostgreSQL it follows the database's collation. PostgreSQL and SQLite only; other databases raise. The generated type is `<Model>OrderObjects`.

### Changed

Faster on every backend. `benchmarks/kitchen_sink` runs 12 workloads (nested connections, `on=` views, filters across several relations, groups and aggregates) over 500 users, 5,000 posts and 25,000 comments on SQLite. All of them are faster on all five backend variants, with identical results.

- **The library's schema extensions skip plain column fields.** Under `orm.schema()`, a scalar or enum field that reads a column straight off a row, Relay's default `id` when it reads a column, and the plain fields of the library's own connection, edge and page-info types are no longer wrapped by the optimizer, batching, connection, lazy-resolution and row-scope `resolve` hooks, none of which act on them. Any other field keeps them: a property can load a relation, which lazy resolution is there to report. An app's own `resolve` extensions still run on every field, as does a subclass of a library extension that overrides `resolve`. A schema built with `strawberry.Schema` directly is unchanged.
- **Django under async execution reads what is loaded on the event loop.** A loaded column, a relation the library prefetched and scoped, a loaded foreign key and Relay's default `id` are read in place instead of through `sync_to_async`, a thread hop per field. A deferred column, a relation given a `filter` or `order`, and a prefetched relation the library did not scope itself, when its type has `scope_rows`, still go to the worker thread. A resolver is no longer wrapped in `sync_to_async` twice. Async Django was about 6.5× faster across the workloads.
- **On Django, a plain column has no generated resolver**, so Strawberry reads it as an attribute rather than building an `Info` per value. A column whose descriptor changes the value it stores (a `FileField`, for one) keeps its resolver, and a row whose class (a proxy or subclass) puts a property or another descriptor over the column is read through it.
- **SQLAlchemy: a filter through a scoped relation uses the scope's WHERE clause** when the scope only filters the related table's own columns. It was embedded as `pk IN (SELECT ...)` inside a correlated `EXISTS`, which SQLite runs again for every outer row. A scope with joins, limits, grouping, nested selects, raw SQL, loader options or `with_loader_criteria`, one that selects another entity, one over a class that shares its parent's table, or one over a relation back to the same table, is still embedded as a subquery. Its `with_loader_criteria` did not apply there; see the Unreleased security notes.
- **SQLAlchemy: counts, aggregates and group counts drop the statement's `ORDER BY`**, unless it has a limit or offset, or a PostgreSQL `DISTINCT ON`, that the order decides.
- **Tortoise: a filterable relation reads the rows the optimizer prefetched**, rather than querying again per parent, when it is given no `filter` or `order`. A cache the library did not scope is still queried when the related type has `scope_rows`.
- **A group's `items` are not scope-checked again per group.** They are read from the connection's already scoped query.

### Fixed

- **Tortoise: `orm.order()` and `orm.group()` before `Tortoise.init`** no longer fail on a reverse or many-to-many relation known only by its annotation (`posts: fields.ManyToManyRelation["Post"]`). Before init, the annotation tells whether the relation is to-many.
- **`auto` honours `null=True` on Django and Tortoise.** A nullable column was typed non-null, so a row holding NULL failed with "Cannot return null for non-nullable field". It is typed nullable now, as on SQLAlchemy. This changes the generated schema for such columns.
- **Groups and aggregates work without a `context_value`.** A connection executed with no context returned `null` for both. Under `orm.schema()`, their state is now kept for the execution instead.
- **`orm.connection.lazy(resolver=fn)` on an `@orm.type`** was removed by the decorator, leaving a field with no `first`, `filter` or `order` arguments. The keyword form now builds the same field as the decorator form.
- **A generated connection applies its `filter` and `order` once**, not twice.

### Fixed

- **An `on=` view's rows are trusted as a read of its relation** (the `on=` view brief). A view named differently from its relation (`recent = orm.field.eager(on="books", scope=...)`) had its prefetched, already scoped rows scope-checked and loaded again, a parent at a time. It is now decided by the relation the field reads. A field whose resolver returns rows it read itself is still checked. On Django, a nested selection under such a view is prefetched with it, rather than per row.
- **A batched field under a connection is batched (SQLAlchemy item 1).** A connection's edges now record their nodes as the parents of what is read under `node`, so an `on=` view or other batchable field under a connection is one statement for the page instead of one per node.
- **The batcher's rows are not scoped and loaded again per parent (item 2).** They are marked as read with the scope and the nested selection already applied. Under async execution, one batch is shared by every parent rather than awaited once per parent.
- **Rows a resolver hands back are loaded in their own session, and only what they lack (item 3).** SQLAlchemy's `load_relations` re-reads rows in the session they belong to, so the caller's instances get the relations, and skips relations every row already has loaded, descending into loaded ones. Rows that already hold the selection cost no statement. A detached row is filled from a copy read in the request's session. Parent keys are sent 500 to a statement. **Limit:** a relation through an association table (many-to-many), on a composite key, or whose `primaryjoin` says more than the key comparison still uses `selectinload`, and the scope's order is lost.
- **A scope check reads only keys (item 6).** `filter_scoped_pks` selects the primary key column, so loader options a `scope_rows` attaches are not run for a membership check.
- **`SmallInteger` and `BigInteger` columns are `Int` (item 7)**, not `String`, and get `sum`/`avg` aggregates. A column type is now looked up by its class and each class it derives from, so other subclasses of a known type change too: `Double`, `DOUBLE`, `DOUBLE_PRECISION` and `REAL` become `Float`, MySQL's `TINYINT` and `MEDIUMINT` become `Int`, and `MatchType` becomes `Boolean`. This changes the generated schema for models with such columns.
- **Date and datetime filters compare as dates (item 11).** Every value a lookup compares (`exact`, `neq`, `gt`, `gte`, `lt`, `lte`, `inList`, `notInList`, `range`) is parsed and bound in the column's own type, so PostgreSQL with psycopg 3 no longer refuses `timestamp >= varchar`. A value that is not ISO 8601 (`"2026-09"`) is now refused with an error naming it, rather than handed to the database. Tested on SQLite and by the bound types; the PostgreSQL behaviour follows from the binding.
- **`object: {books: {isNull: true}}` works on a to-many relation (item 12)**, through a foreign key or an association table: rows with no related row the reader can see. `false` gives rows with at least one.
- **A sync session no longer needs greenlet (item 13).** The SQLAlchemy backend looks for `AsyncSession` only once `sqlalchemy.ext.asyncio` has been imported.
- **On Django, a date grouped by an interval through a related type with `scope_rows`** read as a datetime (`"2026-01-01T00:00:00+00:00"`), and a datetime's period did not read in the current time zone. The period is now cut outside the scope's `CASE`, so it reads as it does on the model itself.

- `orm.schema(schema_class=...)` builds a `strawberry.Schema` subclass of your own, with the library's extensions mounted.

### Changed

- On an `@orm.type`, a `strawberry.field(metadata=...)` that sets nothing else no longer replaces the model attribute's resolution. It used to stop Django and Tortoise from generating the relation's resolver.

## 0.22.0

### Added

- `orm.mutations.upsert_node_input(model=, project=, name=)` builds a standalone `{where, create, update}` upsert root for one model. `_meta.upsert.where` accepts a field list or `True` for caller-chosen optional fields.
- `_meta.name` names a projection's generated types and lets a projection recurse; `_meta.upsert.optional` makes a listed `where` optional.
- Insert-only (find-or-create) upserts:
  - `_meta.upsert.onMatch` chooses what a matched row does: `"UPDATE"` (the default), `"IGNORE"` or `"APPEND"`.
  - `_meta.immutable: True` removes `update`, `unlink`, `delete` and `onReplace`, and matches with `"APPEND"`.
  - `_meta.upsert.onMatchLinks: "IGNORE"` skips forward links sent for a matched row instead of rejecting them.
  - `_meta.maxVisits` caps how often a model may appear on one nesting path.
  - Contradictory keys raise `ValueError` naming the model and keys.
- `orm.apply_upsert(input, info, *, authorize=None)` executes an upsert input on all three backends as one unit of work: a savepoint on SQLAlchemy (sync and async), `transaction.atomic()` on Django (sync and async), and `in_transaction()` on Tortoise. It validates the whole payload first and raises `UpsertValidationError`, `UpsertNotFoundError` or `PermissionError`.
- `AbstractRepo.find_for_upsert`, `find_for_upsert_async`, `can_upsert` and `on_match`.
- Generated upsert inputs carry `__upsert_policy__`; `__relation_policy__` gains `on_match`, `immutable` and `max_visits`.
- `make_ref_type(..., descriptions=)` sets GraphQL descriptions on its variants.

### Changed

- **`apply_ref_list` now applies the `upsert` arm.** It used to drop it silently. The item is found or created under the parent row and linked, on every backend. On Django and Tortoise, a ref list containing an upsert runs in one transaction, so an error part way leaves no rows.
- **Single links without an `onReplace` field are `@oneOf`.** Previously a payload with several operations was resolved by precedence. This covers update-only links, links whose `onReplace` is narrowed to one option, and links to immutable targets. A link that offers `onReplace` stays a plain input, because `onReplace` is sent alongside `create` or `upsert`.
- A projection with no update operation generates no `*Patch` or `*Update` types. `update_node_input()` raises `ValueError` for a model whose projection has none, instead of building an update branch from every field.
- Projections that use none of the new keys generate the same SDL as before, apart from the `@oneOf` change above.

### Fixed

- `AbstractRepo._create_async` and `_save_async` await the flush on a SQLAlchemy `AsyncSession`, so the row has its primary key when the call returns.
